# 图文素材压缩、续传与恢复

## 压缩预算

读取当前平台界面的单图、总文件体积和格式限制。知乎 DOCX 曾显示 30 MB 限制，此值需以本次界面为准；预留上传余量，不把超过上限的文件送入编辑器等待超时。

原图与 manifest 保持不变。派生图片可用 Pillow 的 `ImageOps.exif_transpose` 校正方向，以 RGB JPEG、最长宽高预算约 1400×2000、quality 85、optimize 作为大图周报的起点；存在透明背景、动画或细小文字时选择保留其含义的格式与尺寸。检查可读性，再按体积预算调整；不能删图、裁掉正文或改变图序来凑限额。

从原 blocks 顺序生成嵌图 DOCX，图片使用优化后的本地文件，文字及来源保持一致。检查 `word/media/` 和 `word/document.xml` 中嵌图对象数量，并比对嵌图关系的顺序；重复使用同一图时 media 文件数可能少于图片对象数，以每个图片块对应的嵌图对象为准。生成后计算实际文件字节数，不仅估算图片总大小。

## 上传缓存与部分失败

缓存存仓库外，按来源 manifest SHA-256、平台、账号和范围绑定；每条图片保存 `order`、`source_sha256`、优化文件路径、平台托管 URL、成功终态和核验时间。成功项立即落盘，失败项单独列出。裸 URL 数组必须另有同来源、账号、范围与顺序的核验证据才能复用。

上传中断后保留成功 URL，只补传失败或未上传的项；按原 `order` 合并，不按上传完成时间排序。完成后检查每个图片块恰有一个成功映射，全部 URL 是平台可持久访问的 HTTPS 托管地址，数量与原素材一致。部分失败没有可靠序号映射时，先从编辑器或原上传记录恢复映射；未能证明顺序就停在发布前，不能猜测。

小黑盒批量上传“pending=0、成功数不足”表示失败，不能一直等待总数追平。微博 HTTP 200 或异步 `TaskProcessing` 只表示请求被接收；必须等最终任务成功并确认编辑器节点托管 URL。

## 恢复范围与验收

保留成功图片、原草稿和已公开平台，修复只作用于失败图片/平台；每次修复之后重新核对全文、图片数量及原顺序。使用本次已有素材，不再次抓取来源。平台持续返回明确错误、需要登录/验证码、映射无法恢复或超出保真压缩预算时记录原因并停止该平台，不循环提交。

公开页全文可以归一化 NFC、排版空白与平台注入的零宽字符；编辑器校验还要排除其明确的 UI 占位说明。不能用前后几句或字数相等代替全文一致。图片顺序按每个平台已核验的托管图片标识比较，允许 CDN 主机与缩略规格变化，但不能将两张不同图片归成同一个标识。
